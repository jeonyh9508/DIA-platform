# DIA 프로젝트 – 공방 예약 · 정산 · ERP 통합 플랫폼

공방 체험 예약 서비스를 중심으로  
이커머스 기능과 공방주/관리자용 ERP 시스템을 함께 제공하는 플랫폼입니다.

사용자는 클래스 예약과 결제를,  
공방주는 프로그램 운영과 정산을,  
운영자는 승인·정산·지표 관리를 하나의 시스템에서 처리할 수 있도록 구성했습니다.

기능을 많이 만드는 것보다  
**운영 과정에서 실제로 필요한 흐름이 끊기지 않도록 설계하는 것**에 집중했습니다.

---

## 사용 기술

- Backend: Java 17, Spring Boot, MyBatis, Spring Security
- Frontend: React, JavaScript(ES6), HTML5, CSS3
- Database: MySQL 8.0
- WAS: Apache Tomcat 10.1
- API: Kakao Maps API, Naver SMTP API
- Tool & Collaboration: IntelliJ, VS Code, Git, GitHub, Notion, Slack, Figma

## 구현 과정에서 고민했던 부분

### 공방 정산 자동 처리 중 데드락 문제

예약 결제 → 수강 종료 → 정산 처리 흐름을  
`@Scheduled` 작업으로 1분 주기로 자동 처리하도록 구성했습니다.

초기에는 정산 데이터를  
**UPSERT 방식**으로 한 번에 처리하려 했지만,

특정 시점에서는 정상 처리되고  
특정 시점에서는 MySQL 데드락이 발생하는 문제가 반복되었습니다.

원인을 추적한 결과,

- 동일한 공방 / 프로그램 / 월(monthly) 기준으로  
  동시에 정산 데이터가 갱신되는 구조
- UNIQUE KEY와 UPSERT가 함께 사용되며  
  트랜잭션 충돌 가능성이 높아진 상황이었습니다.

이후에는

- 정산 대상 예약을 먼저 조회
- 처리 완료 여부를 나타내는 `profit_paid` 컬럼을 기준으로 상태 관리
- 조회 → 처리 → 상태 업데이트 흐름으로 분리

하는 방식으로 구조를 수정했습니다.

그 결과,
정산 중복 처리와 데드락 문제를 동시에 해결할 수 있었고,  
정산 로직의 흐름도 훨씬 명확해졌습니다.

---

### 정산 데이터 구조 설계

정산은 단순 합계가 아니라  
조정·환불까지 고려해야 하는 영역이었습니다.

- `profit` 테이블:  
  공방/프로그램 단위 수익과 정산 상태 관리

- `settlement` 테이블:  
  월별 정산 금액, 조정 금액, 최종 납부 금액 관리

조정이 발생한 경우에는

- 기존 정산과 분리된 데이터로 관리
- 환불 시에는 전액 차감 처리
- 공방주 화면에서는  
  기본 수익 정보는 `profit` 기준으로 유지하되  
  영수증은 조정된 금액 기준으로 표시

하도록 구성했습니다.

정산 금액이 왜 이렇게 나왔는지  
공방주가 스스로 이해할 수 있도록  
데이터 흐름과 화면 구성을 함께 맞추는 데 신경 썼습니다.
